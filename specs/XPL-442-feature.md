## Problem

The team reviews Compose idioms, Views lifecycle, accessibility, tests, threading correctness, security and architecture, but nobody asks **what a change costs at runtime or in the integrator's APK**: a bitmap decoded on every adapter bind, a page list held as full `Bitmap`s in UI state, a gesture that recomposes a whole `LazyColumn` per frame, a Koin graph re-loaded with an `Activity` on every facade call, a dependency that ships megabytes of model binaries to every integrator, or a `consumer-rules.pro` line that stops R8 from stripping anything in the host app. Today the orchestrator's rule 11 says performance standards are "enforced inline (see Mandatory Rules)", but Mandatory Rules has no performance bullet and `AGENTS.md` has no performance section — the inline enforcement points at rules that do not exist. `code-reviewer` says outright that performance has no specialist, and `architecture-specialist` lists `performance-specialist` as "planned but not written yet". XPL-402 asks for it, and the iOS repo has its twin.

## Decisions (clarifying questions, 2026-10-15)

| Question | Decision |
|---|---|
| Boundary with `concurrency-specialist` on the main thread | **Cost vs blocking split.** `concurrency-specialist` keeps *blocking calls* on main (`runBlocking`, `Tasks.await`, `Future.get`, DataStore `first()`, file I/O). `performance-specialist` owns *expensive-but-legitimate* work on hot paths: bitmap decode/encode/crop in a capture callback, adapter `onBind`, `@Composable` bodies and draw, per-frame allocation. When both apply (e.g. `CameraXController.onCaptureSuccess` cropping on the main executor), performance reports the cost and hands the thread move to concurrency. |
| Shared rules file | **None.** Rules live in `performance-specialist.md` only (like `android-security-specialist` and `a11y-specialist`). `code-reviewer` escalates to it. The orchestrator's rule 11 is reworded to localization-only so it stops pointing at rules that do not exist. No `.claude/rules/performance.md`. |
| Hotspots found during exploration | **Listed for tickets, not fixed** (same as XPL-443). They become the agent's "known existing patterns" and the dry-run material. No Kotlin/Gradle change in this PR. |
| Tooling | **No-build-change recipes only; ask for the rest.** The agent may prescribe Android Studio Profiler, Layout Inspector recomposition counts, `adb shell dumpsys gfxinfo`/`meminfo`, `./gradlew … dependencies` and AAR-size checks. Anything that touches a build file (Compose compiler metrics flags, LeakCanary or StrictMode in an example app, a benchmark module, baseline profiles) is an "ask the user" item — the repo has none of them today. |
| File name | `.claude/agents/performance-specialist.md` — no `android-` prefix, like `concurrency-specialist` and `architecture-specialist`. |
| Severity | `blocker` / `warning` / `nit`, same as the Android siblings (ticket). |
| Tools | `Read, Edit, Write, Glob, Grep` — same as the siblings (ticket). |

## What the code really does (verified on this branch, 2026-10-15)

Facts the agent states as patterns plus the `grep`/`ls` to re-check them — never as counts, never with line numbers.

### Camera and image pipeline (capture-sdk)

- `internal/camera/api/camerax/CameraXController.kt` builds three CameraX use cases with one `ResolutionSelector` (`ResolutionStrategy` with `FALLBACK_RULE_CLOSEST_HIGHER_THEN_LOWER`): `Preview`, `ImageCapture` with `CAPTURE_MODE_MAXIMIZE_QUALITY`, and `ImageAnalysis` with `STRATEGY_KEEP_ONLY_LATEST`. The analyzer and the `takePicture` callback both run on `ContextCompat.getMainExecutor(activity)` — a design the concurrency agent already records; the performance agent reviews the *cost* of what runs there.
- **Capture path, all on the main executor:** `onCaptureSuccess` calls `ImageProxy.toCroppedByteArray()` from `camerax/Extensions.kt` — a full copy of the JPEG plane, and when `cropRect` differs from the frame size a `BitmapRegionDecoder.decodeRegion` plus `Bitmap.compress(JPEG, 100)` re-encode — then `PhotoFactory.newPhotoFromJpeg` → `MutablePhoto` → the `ImmutablePhoto` constructor, which calls `createPreview()` (`BitmapFactory.decodeByteArray` with `inSampleSize` 8 when the JPEG exceeds `PREVIEW_SHRINK_WEIGHT` kilobytes, else 2). Re-check: `grep -n 'getMainExecutor\|toCroppedByteArray\|newPhotoFromJpeg' capture-sdk/sdk/src/main/java/net/gini/android/capture/internal/camera/api/camerax/CameraXController.kt`.
- **Edit path, off main:** `internal/camera/photo/PhotoEdit.java` applies `PhotoRotationModifier`, `PhotoCompressionModifier` (default JPEG quality constant `DEFAULT_JPEG_COMPRESSION_QUALITY`) and `PhotoCropModifier` in an `AsyncTask` via `applyAsync`, or synchronously via `apply()`. `PhotoCropModifier` decodes the full photo, rotates, crops, re-encodes and recycles the three bitmaps.
- **Frame path:** `setPreviewCallback` installs an `ImageAnalysis.Analyzer` on main that forwards `imageProxy.image` to `CameraInterface.PreviewCallback.onPreviewFrame(image, size, rotation, closeCallback)`; `imageProxy.close()` runs only when the callback says processing finished, so a frame stays allocated until QR detection (`internal/qrcode/QRCodeDetectorImpl.java`'s `HandlerThread`, blocking `Tasks.await` in `QRCodeDetectorTaskMLKit.java`) and text recognition (`internal/textrecognition/MLKitTextRecognizer.kt`, `InputImage.fromMediaImage`, Task listeners on main) are done. `camera/CameraFragmentImpl.java` ref-counts the frame with an `AtomicInteger`.
- **Thumbnails and previews:** `camera/PhotoThumbnail.java` caches one rotated copy per `ThumbnailBitmap`; `review/multipage/previews/PreviewPagesAdapter.kt` asks `GiniCapture.getInstance().internal().photoMemoryCache[...]` in `onBindViewHolder` and sets `bitmapPreview`; `internal/document/ImageDocumentRenderer.java` builds previews with `PhotoFactoryDocumentAsyncTask`; `analysis/AnalysisFragmentImpl.java` `showBitmap` sets the preview; zoom uses the vendored `com/ortiz/touch/TouchImageView.java` through `review/RotatableTouchImageViewContainer.java` and `review/zoom/ZoomInPreviewFragment.java`.
- **Imports:** `ImportImageFileUrisAsyncTask.java`, `camera/ImportImageDocumentUrisAsyncTask.java`, `internal/fileimport/AbstractImportImageUrisAsyncTask.java`; `internal/util/ExifOrientationReader.kt` reads EXIF from a stream; `internal/storage/ImageDiskStore.java` copies bytes/streams to files.

### Memory model (capture-sdk)

- `internal/cache/MemoryCache.java` — abstract `LruCache` plus a worker queue with a running-workers limit and per-key waiting callbacks. `PhotoMemoryCache` (keyed by `ImageDocument`, `sizeOf` = preview `getByteCount()/1024`) and `DocumentDataMemoryCache` (keyed by `GiniCaptureDocument`, `byte[]`, `entryRemoved` → `key.unloadData()`) each take **one eighth of `Runtime.maxMemory()`** — so the two together may hold a quarter of the host app's heap. Both are owned by the `GiniCapture` instance; `GiniCapture.newInstance` cleans up the previous instance.
- `internal/camera/photo/ParcelableMemoryCache.java` — enum singleton with a static main-looper `Handler` and a `ConcurrentHashMap`, keeping `byte[]` and `Bitmap` payloads out of `Parcel`s (avoids `TransactionTooLargeException`) with a delayed remove (`REMOVE_DELAY_MS`). `ImmutablePhoto.writeToParcel` stores the preview bitmap there.
- `internal/document/ImageMultiPageDocumentMemoryStore.java` holds one `ImageMultiPageDocument` reference.
- Re-check: `grep -rln 'LruCache\|ParcelableMemoryCache' capture-sdk/sdk/src/main/java`.

## Design

### 1. `.claude/agents/performance-specialist.md`

Same section order as `architecture-specialist.md` and `concurrency-specialist.md`. No line numbers, no counts; every path, class, catalog alias and tool named must exist on the branch.

1. **Frontmatter** — `name: performance-specialist`; description: "Runtime-cost reviewer for the Gini Android SDKs. Finds work that costs frames, memory or APK size with a user-visible consequence: the capture-sdk camera and bitmap pipeline (CameraX callbacks, JPEG decode/encode, previews, the LruCaches and ParcelableMemoryCache), Compose recomposition cost in capture-sdk/bank-sdk, RecyclerView/ViewPager2 bind cost in health-sdk, internal-payment-sdk and the legacy capture screens, Koin graph and facade init cost, and what every dependency and consumer-rules line ships to the integrator. Reviews diff-first with an SDK model: no Application scope, the host app owns R8 and the heap. Threading correctness stays with concurrency-specialist."; `tools: Read, Edit, Write, Glob, Grep`.
2. **The most important fact — these are SDKs, not an app.** The host app owns the heap, the main thread, R8 and the APK: a bitmap we keep is memory the integrator's screens lose; a `consumer-rules.pro` keep rule constrains *their* R8; every `implementation` line ships its transitive tree (and `api` lines ship it to their compile classpath); the SDK cannot tune device-class behaviour from an `Application` it does not own; `minSdk 23` means low-end devices with small heaps; a capture flow is a few screens inside a banking app, so init cost is paid on every entry into the flow, not once at app start.
3. **Repo Context** — the facts from §What the code really does, each with its re-check command, grouped as there: camera and image pipeline; memory model; Compose; lists and Views; Koin and facade init; dependencies, R8 and size; the absence of tooling.
4. **Knowledge Source** — read **`.claude/rules/coroutines-flow.md`** for threading (owned by `concurrency-specialist`; cite, never restate; hand any dispatcher/scope/blocking finding to that agent). There is no shared performance rules file; the rules below are the only set. `AGENTS.md` wins on conflict. Sources behind the rules: Android developers' performance guides (app startup, rendering/jank, memory, bitmaps — `inSampleSize`/`inJustDecodeBounds`, `BitmapRegionDecoder`, `LruCache`), the Compose performance and stability documentation, the RecyclerView `ListAdapter`/`DiffUtil` docs, Koin's definition-kind docs (`single`/`factory`/`createdAtStart`), ML Kit's bundled-vs-unbundled guide, and the R8/consumer-rules documentation. No external skill package is vendored; don't cite community skill packs as authority.
5. **Core Instructions**
   - **A cost claim names the path and the trigger.** "Decoded on every `onBind` of `DocumentPageAdapter`, i.e. on every page swipe and recycle." Without a named path and trigger it is a preference — leave it out.
   - **A finding names the user-visible consequence.** Dropped frames during which interaction; how much memory relative to the heap (use the 1/8-heap caches as the yardstick); leaked until which event; how many megabytes added to the integrator's APK; how much longer the flow takes to open. No consequence, no finding.

## Hotspots found (for tickets — not fixed here)

Ranked by user-visible cost. Each needs a ticket decision by the user. All verified by reading on this branch; none fixed in this PR.

1. **Capture callback does the whole image pipeline on the main thread** — `CameraXController.onCaptureSuccess` (main executor) copies the full-resolution JPEG, region-decodes and re-encodes it at quality 100 when the preview crop differs from the sensor frame, then `MutablePhoto` → `ImmutablePhoto` decodes the preview (`inSampleSize` 2 or 8). With `CAPTURE_MODE_MAXIMIZE_QUALITY` this is hundreds of milliseconds of frozen UI after the shutter on mid-range devices. Fix direction: move crop/encode/preview into the existing `PhotoEdit` `AsyncTask` path or a background executor and complete the `CompletableFuture` from there — a thread move, so co-owned with `concurrency-specialist` (its high-risk list already names the camera pipeline). Overlaps concurrency hotspot territory; record once.
2. **health-sdk page adapter decodes every page twice per bind on main** — `review/pager/DocumentPageAdapter.kt` `PageViewHolder.onBind` calls `BitmapFactory.decodeByteArray` on the page bytes twice in a row (two `setImageBitmap` calls), without `Options`, on every page swipe and recycle. Fix direction: decode once, at display size, off main (the `Resource` already arrives from a coroutine), keep the decoded bitmap on the `Page` or in a bounded cache.
3. **capture-sdk Koin graph re-loaded with an `Activity` on every bank facade call** — `BankSdkIsolatedKoinContext.init` runs `CaptureSdkIsolatedKoinContext.koin.loadModules(listOf(module { single { context } }))` on each call, and `CaptureFlowActivity.onCreate` passes `this`; `GiniBank.setCaptureConfiguration` additionally re-loads `captureSdkDiBridge` each time. Consequence: the capture graph can retain a destroyed `CaptureFlowActivity` until the next `init` or process end, and the graph is mutated on a per-screen path. Whether Koin's override drops the previous `single` instance immediately is `(confidence: LOW — verify with a heap dump after finishing the capture flow, or read Koin's InstanceRegistry override path)`. Fix direction: load the context module once with an application context (`context.applicationContext`) and the bridge once; `clean()` unloads them.
4. **`ZoomableLazyColumn` recomposes the whole list on every zoom/pan frame** — `ui/components/list/ZoomableLazyColumn.kt` reads `scale`/`offsetX`/`offsetY` in the non-lambda `graphicsLayer(...)` overload. Consequence: jank while pinch-zooming invoice pages in `InvoicePreviewScreen`. Fix direction: `graphicsLayer { scaleX = scale; … }` so the reads move to the draw phase; `key` on `itemsIndexed(pages)`.
5. **Full invoice page bitmaps in Orbit state** — `InvoicePreviewFragmentState.Ready(images: List<Bitmap>)`, decoded by `LoadInvoiceBitmapsUseCase` without `Options` and kept for the screen's life; every state `copy()` carries the list; an unstable `List<Bitmap>` parameter reaches `ImagesList`. Consequence: memory proportional to page count × page resolution on a flow inside a banking app. Fix direction: decode at display width (`inSampleSize` from `inJustDecodeBounds`), hold immutable wrappers, or page lazily.
6. **capture-sdk declares four dependencies it never uses** — `libs.orbitmvi.compose`, `libs.orbitmvi.viewmodel`, `libs.koin.androidx.compose`, `libs.koin.android.compat` in `capture-sdk/sdk/build.gradle.kts` with no source reference. Consequence: extra artifacts and their trees in every capture-sdk integrator's APK (bank-sdk integrators receive Orbit through bank-sdk anyway). Fix direction: remove, run `/gini-check` and `apiCheck`, confirm the SBOM; `architecture-specialist` co-reviews.
7. **bank-sdk `consumer-rules.pro` keeps every Parcelable in the host app** — `-keep class * implements android.os.Parcelable` and `-keepnames class * implements android.os.Parcelable` apply to the integrator's whole code base. Consequence: R8 cannot strip or obfuscate any Parcelable in the host app once bank-sdk is integrated. Fix direction: scope the rules to `net.gini.android.bank.sdk.**`; `architecture-specialist` asks why on every consumer-rules change, so this is a joint ticket.
8. **Two 1/8-heap caches** — `PhotoMemoryCache` and `DocumentDataMemoryCache` may together take a quarter of the host heap. A design decision to record, not a bug; only worth a ticket if an integrator reports memory pressure.
9. **`MutablePhoto` constructor does EXIF work on the capture callback** (found by the T8 audit dry run, verified) — after the preview decode, `readRequiredTags()` and `updateExif()` run two commons-imaging metadata parses and an `ExifRewriter` full-JPEG copy on the main executor, and the result is rebuilt again by every modifier in the edit chain. Extends hotspot 1; same fix direction and the same co-ownership with `concurrency-specialist`.
10. **Camera edit chain encodes twice** (T8, verified) — `PhotoEdit.crop()` already encodes at `DEFAULT_JPEG_COMPRESSION_QUALITY`, and `CameraFragmentImpl` chains `.crop(...).compressByDefault()`, so the cropped image is decoded and re-encoded a second time at the same quality, with `updateBitmapPreview()` and `updateExif()` repeated per modifier. Consequence: roughly double the wait before the review screen and a second full-size transient bitmap, plus a second generation of JPEG loss. Fix direction: one preview/EXIF pass at the end of `applyChanges`, skip the compression modifier when the crop succeeded.
11. **`CameraLifecycle` is never destroyed** (T8, library behaviour unverified) — `CameraXController.close()` moves the owner to `CREATED`; `unbindAll()` runs only in the next `open()`. If CameraX keeps the bound use cases until `ON_DESTROY` or `unbindAll()`, the controller, the `PreviewView` and the host Activity stay reachable from a process singleton between flows. Verify with a heap dump; fix direction: move the registry to `DESTROYED` in `close()` and recreate the owner per `open()`.
12. **Two more unused capture-sdk dependencies** (T9, grep-verified, not compile-verified) — `libs.navigation.ui.ktx` and `libs.compose.activity` have no import in any capture-sdk source set. Joins hotspot 6.
